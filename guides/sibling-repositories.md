# Sibling Repositories

The format this repository uses, fictional scenarios, evaluated workflows, honest real-use testing, is not inherently specific to B2B sales. The same shape could in principle apply to finance, HR, operations, project management, or any other business function. This is not a plan for this repository, and it is not scoped. It is a scoping guide: what would actually need to be true before a sibling repository for another function should start, and what to build first if it does.

Built ahead of any such repository actually starting, on the project owner's own call, the same way several other backlog ideas were written up ahead of their usual bar tonight. Unlike most of those, this one has a hard precondition below that a spec alone cannot satisfy.

## The One Hard Condition

A sibling repository only works with a genuine practitioner from that function driving it, the same way this repository only works because a real salesperson is testing real sales workflows against real deals. Do not start drafting one of these without that person in place. A repository built by someone outside the function, however carefully, would be guessing at what the real jobs are and what a good output actually looks like, which is exactly the failure mode this repository's own fictional-content and honest-evaluation rules exist to prevent.

This condition is not a formality to note and move past. It is the actual bottleneck. Everything below assumes it is already met.

## What Transfers Directly

- **The house style discipline.** Plain, direct language, no filler, no manufactured urgency, evidence labelled as confirmed, estimated, inferred, or unknown. None of this is sales-specific.
- **CONTRIBUTING.md's completeness bar.** A guide, a bounded instruction where repeatability genuinely matters, fictional source material, a completed output, an honest evaluation against a rubric, known failure conditions, and explicit human approval points. This structure does not depend on the function.
- **The repository-checks discipline.** A deterministic scanner for broken links, placeholder text, and accidentally committed private material applies to any function's version of this repository just as it does here.
- **The public-data boundary.** No real customer, client, employee, or confidential employer information in tracked files, the same rule as [RESPONSIBLE-USE.md](../RESPONSIBLE-USE.md), regardless of which function the repository serves.

## What Does Not Transfer, and Needs the Practitioner to Define

- **What the real jobs actually are.** This repository's sixteen jobs came from an actual salesperson's actual week, not from a generic list of sales activities. A finance, HR, operations, or project management sibling needs its own practitioner naming its own real, recurring jobs the same way, not a sales list relabelled with different words.
- **What a good output looks like.** The [sales AI output rubric](../evaluations/sales-ai-output-rubric.md)'s ten areas are generic enough to adapt, but what counts as a strong answer to "did this correctly separate confirmed information from an inference" looks different in a finance reconciliation than in a sales pipeline review. The practitioner defines that, not an adaptation of this repository's own worked examples.
- **What real evidence and real testing mean in that function.** This repository tests workflows against a practitioner's actual deals. A sibling repository needs its own equivalent real material, real accounts, real requests, real decisions, from someone who actually does that job, not a fictional scenario dressed up as evidence.

## What to Build First, Once the Practitioner Is in Place

Not the whole repository at once. The same order this one grew in: one real job the practitioner does often, built to CONTRIBUTING.md's full completeness bar, tested against one real, anonymised case from that practitioner's own work, and honestly evaluated. If that one job holds up, the second follows the same way this repository's later verticals did, each new one tested rather than assumed to work because the first one did.

## What This Guide Is Not

This is not an announcement that a sibling repository is starting, and it names no specific function, no specific practitioner, and no timeline. It exists so that if and when a genuine practitioner from another function wants to build one, the scoping question, what transfers and what has to be redone from scratch, does not have to be worked out again from nothing.
