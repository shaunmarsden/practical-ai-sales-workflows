# Sibling Repositories

The format this repository uses (fictional scenarios, tested workflows, and real-use testing reported as it happened) isn't tied to B2B sales. The same shape could work for finance, HR, operations, project management or any other business function. This isn't a plan for this repository, and it has no scope. It's a guide to scoping one: what would need to be true before a sibling repository for another function should start, and what to build first if it does.

I wrote this before any such repository started, as I did with several other backlog ideas. Unlike most of those, this one has a hard condition, below, that no written plan can meet.

## The One Hard Condition

A sibling repository only works if someone who does that job for real drives it. This one only works because I'm a salesperson testing sales workflows against real deals. Don't start drafting one without that person in place. Someone outside the function, however careful, would be guessing at what the real jobs are and what a good output looks like. That's the very failure this repository's rules on fictional content and fair evaluation exist to prevent.

This condition isn't a formality to note and move past. It's what holds everything up. Everything below assumes it's met.

## What Transfers Directly

- The house style. Plain, direct language, no filler, no made-up urgency, and evidence labelled as confirmed, estimated, inferred or unknown. None of this is specific to sales.
- CONTRIBUTING.md's bar for a finished piece of work. A guide, a fixed instruction where repeating the job the same way matters, fictional source material, a finished output, an honest evaluation against a rubric, known ways it fails, and clear points where a person approves. This structure doesn't depend on the function.
- The repository checks. A script that scans for broken links, placeholder text and private material committed by mistake works for any function's version of this repository, just as it does here.
- The line on public data. No real customer, client, employee or confidential employer information in tracked files. It's the same rule as [RESPONSIBLE-USE.md](../RESPONSIBLE-USE.md), whatever function the repository serves.

## What Does Not Transfer, and Needs the Practitioner to Define

- What the real jobs are. This repository's jobs came from a real salesperson's week, mine, not from a generic list of sales tasks. A finance, HR, operations or project management sibling needs its own practitioner to name its own real, recurring jobs in the same way, not a sales list with new labels.
- What a good output looks like. The 10 areas in the [sales AI output rubric](../evaluations/sales-ai-output-rubric.md) are general enough to adapt. But a strong answer to "did this correctly separate confirmed information from an inference" looks different in a finance reconciliation than in a sales pipeline review. The practitioner decides that, not an adapted version of this repository's worked examples.
- What real evidence and real testing mean in that function. This repository tests workflows against my own deals. A sibling repository needs its own real material, such as real accounts, requests and decisions, from someone who does that job. A fictional scenario passed off as evidence won't do.

## What to Build First, Once the Practitioner Is in Place

Not the whole repository at once. Follow the order this one grew in. Take one real job the practitioner does often, build it to CONTRIBUTING.md's full bar, test it against one real, anonymised case from their own work, and evaluate it honestly. If that job holds up, the second follows the same way this repository's later areas did. Test each new one, rather than assuming it works because the first did.

## What This Guide Is Not

This doesn't announce that a sibling repository is starting. It names no function, no practitioner and no timeline. It's here so that if someone who does another job wants to build one, they don't have to work out from nothing what transfers and what has to be redone from scratch.
