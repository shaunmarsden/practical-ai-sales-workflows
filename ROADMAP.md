# Roadmap

I keep this page short. It shows what I'm working on now, what evidence could move next and the ideas I'm saving for later. Finished work goes in the [changelog](CHANGELOG.md) and [GitHub Releases](https://github.com/shaunmarsden/practical-ai-sales-workflows/releases).

## Now

- Keep the feedback form and Discussions link in view wherever someone might be using a workflow. For a project like this, that's how outside evidence will arrive, not through a recruited, moderated session. Log whatever comes in, even a single line.
- Keep testing against real sales work as it comes up. Log useful findings without publishing customer, employer or confidential information.
- Keep the proof in view. Update the [evidence-status matrix](EVIDENCE-STATUS.md) and [visitor feedback log](evaluations/visitor-feedback-log.md) when the evidence changes.
- Get someone outside the project to test the sales-copilot method. The public example has a fictional scored run and one real-use finding from my own build, with private details removed. What's missing is someone else adapting the template with their own approved information, not more command modes.

The gaps are simple. Nobody has used the feedback form or Discussions yet. The sales-copilot method still has no outside test. Move a Stalled Decision now has a real-use finding, but it's a boundary case: a real delay, rightly classed as *not* indecision. I still need a case with a buyer who really is indecisive. No sales job has had a logged test by an outside user.

## Next, Based on User Evidence

I'm not promising these. They move only when real use shows they'd solve a real problem.

- Fix navigation or wording problems that keep stopping people finding and using a workflow.
- Improve a workflow when a real or outside test finds a specific failure.
- Add a skill to a job that doesn't have one yet, currently [Get a Weekly View Without Building a Dashboard](recipes/get-a-weekly-view.md) and [Review an Outbound Campaign](recipes/review-an-outbound-campaign.md), if repeated use shows the method deserves a reusable instruction.
- Revisit the starting routes and bundles if people keep choosing a different route.
- Package some skills for download only if people need a maintained bundle rather than using the repository directly.

## Later

- Plain-English guides to transcript tools, notebooks that answer from your own sources, choosing a model and managing tokens.
- Better voices for the interactive demo, if the improvement is worth the cost and effort.
- The role-play simulator, evidence workspace, lead-qualification view and instruction-testing tool described in [Future Interfaces](guides/future-interfaces.md). These are still design ideas, not working software.
- A harder test of the standard skill-package structure, on a job that doesn't already have a fictional example.
- Sibling repositories for another business function, but only if someone who does that job helps define and test the work.
